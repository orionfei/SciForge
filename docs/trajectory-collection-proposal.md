# SciForge Trajectory 数据收集 Proposal

## 核心意图

我们希望将 SciForge 打造成一个高质量科研 agent trajectory 的收集平台。

这里的 trajectory 指的是：在真实科研任务中，用户和 agent 之间一段有价值的交互过程。它不一定要覆盖一个完整的端到端科研任务，也可以只是某个小目标、小阶段的完成过程，例如修正一个实验设计、补充一个 baseline、改进一段分析、解决一个代码错误，或生成一个更好的研究总结。

它不只包含最终答案，也包含中间的用户反馈、agent 修改、工具调用、失败尝试、纠错过程和最终产物。

核心想法是：

> 将有价值的人机科研协作过程，转化为可复用的训练和评测数据。

## 背景

当前科研 agent 还很难完全自动完成复杂科研任务。在实际使用中，研究者经常需要介入，例如纠正 agent 的理解、指出遗漏的 baseline、判断实验设计是否合理，或者决定哪些中间结果有价值。

这些人工介入本身非常有价值。它们展示了 agent 应该如何从错误中恢复、如何根据反馈调整计划、如何使用工具，以及如何逐步走向一个有用的结果。

如果我们只保存最终答案，就会丢失大部分真正有训练价值的信息。

## 我们希望收集什么

SciForge 应该允许用户在一次任务中选择一段有价值的交互，例如从第 N 条消息到第 M 条消息，并将其保存为一个 trajectory。这个片段可以很长，也可以很短；关键不在于它是否完成了整个科研任务，而在于它是否展示了一个清晰的小目标如何被推进、修正和完成。

一个 trajectory 可以包含：

- 用户的问题和反馈
- agent 的回答和计划
- 工具调用及工具输出
- 代码或文件修改
- 失败尝试和修正过程
- 最终产物
- 用户评分或标签

这比普通聊天记录更有价值，因为它保留了结果背后的决策过程。

## 预期价值

这些 trajectories 可以用于：

- 训练更强的科研 agent
- 评估 agent 的长程任务能力
- 分析常见失败模式
- 改进规划和工具使用能力
- 构建特定科研工作流的数据集

长期来看，这会形成一个持续迭代闭环：

> 人机协作产生 trajectories；筛选后的 trajectories 反过来改进未来的 agent。

这种迭代不需要等到 agent 能完整完成一个大科研任务才开始。我们可以先从许多小阶段、小目标的高质量 trajectories 开始积累，一点一点优化 agent 在具体科研环节中的能力，最终逐步提升整体端到端科研能力。

## 总结

这个 proposal 的核心不是简单保存聊天记录，而是在 SciForge 中建立一个 trajectory 收集机制。目标是把真实科研任务中的高质量人机协作过程沉淀为数据，为后续训练和评估更强的科研 agent 提供基础。
